# 任务分解：识别工作流中的步骤

> [!summary]
> 建 agentic workflow 的关键技能：把「人/业务在做的事」拆成 **离散步骤**，每步问：**LLM、短代码、函数调用或工具 能不能做？** 做不了就再拆。先粗拆 → 看效果 → 对薄弱步 **继续分解**；积木是 LLM / 专用模型 / API·检索·跑代码。下一讲：**Evals**。

来源：吴恩达 《Agentic AI》· P06  
前置：[[02_Agentic]]

> [!tip] 读图颜色
> 🔴 用户输入　⚪ LLM　🟢 工具/其它软件

---

## 1. 核心问题

人和公司每天做很多有用的事。怎么把它拆成 **离散步骤**，让 agentic workflow 跟着走？

```mermaid
flowchart LR
  Stuff[人/业务在做的事] --> Decomp[任务分解]
  Decomp --> Steps[离散步骤 1·2·3…]
  Steps --> Check{每步能否由<br/>LLM / 代码 / 工具完成?}
  Check -->|能| Build[串成 workflow]
  Check -->|不能| Decomp2[再拆更细] --> Check
```

## 2. 例一：研究 Agent（迭代加细）

目标：就主题 X 写一篇有深度的文章。

### 2.1 第 0 版：直接生成

```mermaid
flowchart LR
  U([主题 X]) --> L[LLM 一次写完] --> O([成稿])
  classDef user fill:#fecaca,stroke:#b91c1c
  classDef llm fill:#e5e7eb,stroke:#6b7280
  class U,O user
  class L llm
```

问题：往往只到表面、常识层，不够深。

### 2.2 第 1 版：按「人会怎么写」拆三步

人通常不会一上来就终稿，而是：大纲 → 搜网 → 再写。

```mermaid
flowchart LR
  U([主题 X]) --> S1[① LLM 写大纲]
  S1 --> S2[② LLM 生成检索词<br/>+ 网页搜索]
  S2 --> S3[③ LLM 据检索结果写文]
  S3 --> O([成稿])

  classDef user fill:#fecaca,stroke:#b91c1c
  classDef llm fill:#e5e7eb,stroke:#6b7280
  classDef tool fill:#bbf7d0,stroke:#15803d
  class U,O user
  class S1,S3 llm
  class S2 tool
```

每步自检：

| 步骤 | 能否落地？ |
| --- | --- |
| 写大纲 | ✅ LLM 多数主题够用 |
| 检索 | ✅ LLM 出检索词 + 搜索工具 |
| 据结果写文 | ✅ LLM 吃检索结果再写 |

比直接生成更深，可作为 **合理的第一版 workflow**。

### 2.3 第 2 版：成稿仍「散」→ 再拆「写文」

实现后可能发现：开头 / 中间 / 结尾不一致、不连贯。

人会怎么改？不是一次写死，而是：**初稿 → 审视哪里要改 → 修订**。

```mermaid
flowchart LR
  U([主题 X]) --> S1[① 大纲]
  S1 --> S2[② 检索]
  S2 --> S3a[③a 初稿]
  S3a --> S3b[③b 审视要改处]
  S3b --> S3c[③c 修订]
  S3c --> O([成稿])

  classDef user fill:#fecaca,stroke:#b91c1c
  classDef llm fill:#e5e7eb,stroke:#6b7280
  classDef tool fill:#bbf7d0,stroke:#15803d
  class U,O user
  class S1,S3a,S3b,S3c llm
  class S2 tool
```

演进一览：

```mermaid
flowchart TB
  V0[直接生成 · 1 步] -->|不够深| V1[大纲 → 检索 → 写文 · 3 步]
  V1 -->|仍散、不连贯| V2[写文再拆：初稿 → 审视 → 修订]
  V2 -.->|还不满意| Vn[继续改流程…]
  style V0 fill:#fecaca
  style V1 fill:#fef08a
  style V2 fill:#bbf7d0
```

> [!important]
> 分解不是一次到位：先粗拆 → 跑起来看结果 → **对薄弱那一步继续拆**。

## 3. 例二：订单问询邮件

```mermaid
flowchart LR
  M([客户邮件]) --> S1[① 抽取关键信息<br/>发件人 / 订了什么 / 单号]
  S1 --> S2[② 生成查询 · 拉订单库]
  S2 --> S3[③ 起草并发送回复]
  S3 --> O([发出邮件])

  classDef user fill:#fecaca,stroke:#b91c1c
  classDef llm fill:#e5e7eb,stroke:#6b7280
  classDef tool fill:#bbf7d0,stroke:#15803d
  class M,O user
  class S1 llm
  class S2,S3 tool
```

| 步骤 | 落地方式 |
| --- | --- |
| 抽信息 | LLM |
| 查记录 | LLM + **查订单库** 的函数/工具 |
| 回复 | LLM + **发邮件** API（或先入人审队列） |

三步都能对上「LLM 或 LLM+工具」→ 可实施。

## 4. 例三：发票处理（更短）

PDF 已转成文本之后：

```mermaid
flowchart LR
  T([发票文本]) --> S1[① 抽取字段<br/>开票方 / 地址 / 到期日 / 金额…]
  S1 --> S2[② 调函数写库]
  S2 --> DB[(数据库)]

  classDef user fill:#fecaca,stroke:#b91c1c
  classDef llm fill:#e5e7eb,stroke:#6b7280
  classDef tool fill:#bbf7d0,stroke:#15803d
  class T user
  class S1 llm
  class S2,DB tool
```

两步就够：抽取（LLM）→ 落库（工具）。

## 5. 积木箱：你手里有什么

建 workflow ≈ 用积木 **排顺序、接起来**。

```mermaid
mindmap
  root((积木))
    AI 模型
      LLM / 多模态
        生成文本
        决定调什么
        抽取信息
      专用模型
        PDF→文本
        TTS
        图像分析
    软件工具
      API
        实时搜索
        天气
        发邮件
        日历
      检索
        查数据库
        RAG
      执行代码
        LLM 写代码并在本机跑
```

> 工具细节后面模块再展开；此刻先建立「有哪些积木」的直觉。

工作方式：

```mermaid
flowchart LR
  Work[人/业务在做什么] --> Blocks[手头积木]
  Blocks --> Seq[怎样排序组合]
  Seq --> WF[agentic workflow]
```

越清楚积木有哪些，越容易想象能搭出什么。

## 6. 拆步心法（常问两句）

```mermaid
flowchart TB
  Step[看着某一步] --> Q1{LLM 或工具<br/>（API / 函数）能做吗?}
  Q1 -->|能| Keep[留下，接入 workflow]
  Q1 -->|不能| Q2[人会怎么做这一步?]
  Q2 --> Smaller[拆成更小步骤]
  Smaller --> Q1
```

| 问题 | 作用 |
| --- | --- |
| ① 这一步能否用 LLM 或工具实现？ | 判断是否「可落地」 |
| ② 若不能：人会怎么做？能否再拆细？ | 把不可行步变成可行微步 |

---

## 7. 带走

1. **关键技能**：识别离散步骤，并用 LLM/工具实现  
2. **迭代**：粗拆 → 看效果 → 对弱步再分解（研究 Agent 就是范例）  
3. **积木**：模型 + API/检索/跑代码；工作是 **排序组合**  
4. 做不了就问：人怎么做？→ 再拆  
5. 下一讲：**Evals（评估）**——驱动持续改进  

```mermaid
mindmap
  root((任务分解))
    问每步能否落地
      LLM
      工具
    不够就再拆
      像人会怎么做
    积木排序
      模型
      API / RAG / 代码
    多轮迭代
      直到效果够好
```
